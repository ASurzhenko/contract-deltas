# Decisions

One row per choice, with what it cost. The numbers quoted anywhere else come from `results/headline.md`.

| # | Decision | Chosen | Why | What it cost |
|---|---|---|---|---|
| 1 | How to get structured output | Bedrock Converse with one forced tool call (`toolChoice: tool`), `temperature` 0 | The schema is enforced at the API edge and the same dict validates the answer on the way back. Verified live on the default model before relying on it | A model that does not support forced tool choice needs the `any` fallback; the code does not switch automatically |
| 2 | One schema, two uses | `CHANGES_SCHEMA` is both the tool input schema and the `jsonschema` validator input | One source of truth, no drift between what is asked and what is accepted | Rules JSON Schema cannot express (one change per clause type) live in code and in the prompt |
| 3 | Dataset | Generated from one spec in `scripts/generate_dataset.py`, files committed, a test regenerates and compares bytes | 24 documents by hand invite text/label mismatch; labels come from the spec, not from any model | The labels share an author with the documents and the prompt rubric, so independence from the task designer is not real |
| 4 | Noise in the data | Cosmetic edits (number words, shall/will, dates, signatories, two reordered clauses) and two clause types that never change | Without them the task is a string diff and cannot show false positives | One real model error appeared on a reordered clause pair and is kept in the numbers |
| 5 | Lost deals | `signed.md` is the last negotiated text, not a signed contract | A lost deal has no signature but still has a final version to compare | README says so |
| 6 | Matching rule | Match on (deal, clause type); strict row also requires the change kind | A clause changes at most once per deal, so the key is unambiguous | A model that finds the right clause with the wrong change kind scores as a hit in the primary row; the strict row shows it |
| 7 | Direction baseline | Always answering buyer-favorable, measured on the same set of matched changes | The label skew in the whole dataset is not the baseline of the matched subset | Direction accuracy is a weak signal on this data and the README says so |
| 8 | Outcomes | `accepted`, `rejected_output`, `error` | A model that cannot answer is a result; an AWS fault is not. An infrastructure failure must never turn into a number | `error` aborts the run, so a flaky network costs reruns |
| 9 | Raw cache | Committed per deal under `results/raw/<model>/`, whitelist of keys, key built from the exact request plus a hash derived from the retry rules | A rerun costs nothing and a reader can audit the real output. Request ids and headers are never copied | A change to the prompt, schema or retry text changes every key and forces a full rerun |
| 10 | Prompt iterations | Counted from `results/runs.jsonl`: one distinct system prompt hash in the whole history, including one single-deal smoke call made before the full run | Twelve deals are easy to overfit by tuning the prompt against them | None. The prompt was written from the schema and generic contract rules, and not edited after the first run |
| 11 | Label fixes | None | A label is changed only if the document text proves it wrong. The audit of every false positive and every missed excerpt found no label error | - |
| 12 | Suggestions | Four rules, no model, thresholds in config, compared with exact fractions, every suggestion cites deal ids | Reproducible, testable, and honest about being a signal rather than a cause | Rules are crude; an LLM-written variant is out of scope |
| 13 | Model | `us.anthropic.claude-sonnet-4-6` | The Claude 5 profiles were not invocable by this account. The model id is configuration | A newer model may do better; `--model-id` swaps it, and the cache key keeps results apart |
| 14 | Residency claim | "Not used to improve the base models and not shared with any model providers", citing the AWS FAQ | The `us.` profile can serve from more than one US region, so a stronger claim would be false | Less to say in the README |
| 15 | Layout | Flat package, no `pip install -e .`, pinned dependencies, `boto3` imported only in `bedrock.py` | Clone, install, run in a minute. The extractor takes any client with `.converse`, so tests need no credentials | None |
| 16 | Run log key prefix | 16 characters of the cache key, not 12 | A 12-character prefix of a hash can be all digits, which looks exactly like an AWS account id and trips the secret scan. One of the 12 first-run lines did | The log format differs from the first design |
| 17 | Cost line | Tokens are exact (summed from stored usage); the price is an estimate from third-party listings | The AWS pricing page could not be read when this was written | The USD figure is approximate |
| 18 | Text stop reason with a tool call | If `end_turn` or `stop_sequence` arrives together with a `toolUse` block, it is handled like `tool_use`: validated, and on failure retried with a `toolResult` carrying the same id | The failure table in the design did not list this case; the model did produce a usable tool call, and discarding it would waste a call | The stop reason alone is not trusted; two tests pin the behavior |
